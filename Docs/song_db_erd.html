This database uses the Many-to-Many (M:M) pattern extensively via junction tables — a core concept in relational database design. Here's every relationship explained.
Song ↔ Artist
song── song_artist_map── artist M : M
A song can have multiple artists (features, collabs). An artist can have many songs. The junction stores position to order primary vs. featured artists.
Song ↔ Album
song── song_album_map── album M : M
A song can appear on multiple albums (deluxe editions, compilations). An album contains many songs. index is the track number.
Album ↔ Artist
album── album_artist_map── artist M : M
Albums can have multiple credited artists. An artist can release many albums. order defines credit ordering (lead artist first).
Playlist ↔ Song
playlist── playlist_song_map── song M : M
A playlist contains many songs; a song can be in many playlists. position preserves custom ordering. Has its own surrogate id (not composite PK) to support YouTube's setVideoId token.
Song ↔ Song (self-join)
song── related_song_map── song Self M:M
A self-referential relationship. Both songId and relatedSongId point back to song.id. This is how "You may also like" recommendation data is stored. With 39,021 rows it's the largest table.
Event → Song
event──FK──▶ song M : 1
Many play events belong to one song. Each row records a single listening session: when it happened (timestamp) and how long (playTime). Used for listening history analytics.
Format → Song (implicit)
format── id ──▶ song 1 : 1 *
No explicit FK defined, but format.id = song.id by convention. Stores the cached audio stream format (codec, bitrate, URL) for offline/cached playback. The absence of an FK means deletion won't cascade automatically — a design tradeoff.
Lyrics → Song (implicit)
lyrics── id ──▶ song 1 : 1 *
No FK constraint, but lyrics.id maps to song.id. Only 32 songs have lyrics saved — lyrics are fetched on-demand and cached. This is a classic optional 1:1 extension pattern.
PlayCount → Song (implicit)
playCount── song ──▶ song M : 1 *
Composite PK: (song, year, month). Designed to store monthly play stats per song. Currently empty — suggests this feature was planned but not yet active. The event table currently handles play tracking instead.
🔑
Primary Key (PK)
A column (or combination of columns) that uniquely identifies every row in a table. No two rows can share the same PK. No PK can be NULL.
In song: id = "dQw4w9WgXcQ" (YouTube video ID) — each song gets exactly one unique ID.
🔗
Foreign Key (FK)
A column that references the PK of another table, creating a link between them. Enforces referential integrity — you can't add a song to an artist that doesn't exist.
In event: songId is an FK to song.id. If a song is deleted, all its events are deleted too (CASCADE).
🔀
Junction Table (M:M)
When two entities have a Many-to-Many relationship, you can't store it directly. A junction table sits in the middle, holding pairs of FKs. It breaks M:M into two 1:M relationships.
song_artist_map links songs and artists. One row = "song X has artist Y at position Z." This is the most common pattern in this database.
🔄
Self-Referential Relationship
A table where a FK points back to the same table. Used to model hierarchies, graphs, or networks within one entity type.
related_song_map: both songId and relatedSongId reference song.id. This represents "Song A is related to Song B" — a graph of songs.
⚡
CASCADE Delete
When a parent row is deleted, all child rows referencing it are automatically deleted too. This keeps the database consistent without manual cleanup.
Delete a song → its rows in song_artist_map, event, playlist_song_map, and related_song_map are all automatically removed.
🧱
Composite Primary Key
A PK made of two or more columns together. The uniqueness constraint applies to the combination, not individual columns.
In song_artist_map: PK is (songId, artistId) together. The same artist can appear on many songs, and a song can have many artists — but each specific pair is unique.
📦
Denormalization
Intentionally storing redundant data to improve read speed — at the cost of potential inconsistency. The opposite of normalization.
song.albumName duplicates album.title. If the album title changed, you'd need to update both places. But it avoids a JOIN when just displaying the song.
🔌
Implicit Relationship (no FK)
Tables linked by convention (matching IDs) rather than a formal FK constraint. Faster to write, but the database won't enforce integrity for you.
format.id and lyrics.id both equal song.id — but there's no FK declared, so deleting a song won't clean up its format or lyrics rows automatically.
🏛️
Room Database (Android)
This is an Android Room database — Google's SQLite wrapper. room_master_table stores a schema hash for migration detection. android_metadata holds the device locale.
The identity_hash in room_master_table changes whenever the schema changes, forcing the app to run database migration code.
