OpenTune vs ViTune · schema comparison

Both are Android music apps that keep their library in a Room database and back it up as a SQLite file. Both are keyed on the YouTube video id, which is why either can be merged into YT AIO. Below is what each one actually records, measured on OpenTune_20260326213635.backup (9583 songs) and ViTune_backup_20250831122626.db (5085 songs), and what that means for an importer reading them.

The short answer

OpenTune records more about a song. ViTune records more about listening. Neither is a superset of the other, so an importer wants both readers rather than one.

OpenTune wins

Artist credits are complete

15276 credits over 9583 songs, and song_artist_map carries a position, so the lead artist is known. ViTune has 6094 credits over 5085 songs, no position column, and a fifth of its songs have no credit row at all — only the free-text artistsText.

OpenTune wins

It knows what you saved and downloaded

song.inLibrary and song.dateDownload separate the songs you chose from the thousands the player merely cached. ViTune has neither, so an importer cannot honestly mark anything as downloaded, only as liked, played or filed.

ViTune wins

Album coverage is far better

2712 albums mapped to 3978 songs, against OpenTune's 29 albums over 286 songs on a library three times the size. OpenTune also denormalises albumName onto the song, which is how it stays usable, but the album table itself is nearly empty.

ViTune wins

Play history is real history

18394 Event rows against OpenTune's 1864, on a smaller library. Both store one row per play with a timestamp and a duration, so both give a true play count; ViTune simply keeps far more of it.

ViTune wins

Lyrics, and a cleaner cache table

244 songs with lyrics against OpenTune's 26, and ViTune splits them into fixed and time-synced synced where OpenTune stores one blob. Format is keyed on songId, which states the one-to-one relationship the schema actually has.

Even

Shape, keys and the junctions

Same idea throughout: a song table keyed on the video id, three junctions to artists, albums and playlists, and detail tables hanging off the song. An importer written for one is structurally the same as an importer for the other.

Feature by feature

Can you get…OpenTuneViTuneConsequence for the importer
Every credited artist Yes, through the junction Partly — junction plus text The ViTune reader has to merge artistsText with the junction, taking order and completeness from the text and canonical spelling from the table.
Credit order Yes, position Only from the text column Lead artist is reliable in OpenTune. In ViTune it is whatever artistsText lists first.
Album per song Sparse table, but albumName saves it Yes, well populated Read the denormalised name first in OpenTune and fall back to the junction; in ViTune the junction is the better source.
Playlist membership Yes, ordered Yes, ordered Identical handling. Both give a running order worth keeping.
Liked liked and likedDate likedAt, null when not liked Equivalent.
In library inLibrary No column A ViTune import cannot distinguish a saved song from a cached one except by liked, played or filed.
Downloaded dateDownload No column Nothing from a ViTune backup is marked Downloaded. Guessing from a cached Format row would be wrong, and a wrong "already have it" stops a download you wanted.
Play count Count event rows Count Event rows Same query. ViTune also sums it into totalPlayTimeMs.
Duration Seconds, but -1 means unknown The string "3:35" Both need coercion. OpenTune's -1 covers 8050 of its 9583 songs and must become "unknown", not a negative length.
Release date date, or year Not on the song A ViTune import has no upload date. It has to come from a later metadata fetch.
Bitrate bitrate and codecs bitrate and mimeType Same information; the container has to be taken off the mime subtype in ViTune.
On-device files Not stored Yes, as local: ids 42 rows in the real backup. They have no video id and nothing to download, so the reader skips them.
Blacklisted songs No column blacklisted The ViTune reader honours it: 14 songs excluded. Importing something the operator hid would be rude.
The one that catches everybody. A generic "scan every table for something that looks like a video id" importer reads related_song_map in an OpenTune backup and Event in a ViTune one. Those are the two largest tables in each file and neither contains a song you chose. Both readers in this project therefore produce rows from the song table alone, and use every other table only to describe those rows.

How this maps onto YT AIO
